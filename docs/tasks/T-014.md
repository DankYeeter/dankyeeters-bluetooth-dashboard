Die Frage, die dieser Auftrag beantworten muss, ist nicht „laufen die Tests

## Was geaendert wurde

`A2dpLinkDumpParser.kt` liest jetzt zwei Zeilen des `A2DP LDAC State:`-Blocks,
die es vorher ignoriert hat: `LDAC adaptive bit rate encode quality mode
index` und `LDAC adaptive bit rate adjustments`. Sie landen als
`LdacStackState.adaptiveBitrateIndex: Int?` und
`adaptiveBitrateAdjustments: Long?` in `LinkLiveModels.kt`.

**Keine sichtbare Aenderung an der Oberflaeche.** Beide Werte werden gelesen
und getragen, aber nirgends angezeigt.

## Der eine Test, auf den es besonders ankommt

`dropouts are loss even when the underflow counter never moved`
(`A2dpTxProbeTest`) ist die Datenhaelfte von **AK-T009-24**. Er faehrt Arm B
aus T-008 ueber den echten `sampleBetween`-Pfad: 97 000 ms, 525 dropped,
21 dropouts, **underflows 0**, erwartet `hasLoss == true`.

Hintergrund, damit du weisst, warum dieser Fall existiert: `underflow` blieb
im hoerbar kaputten Arm bei exakt 0, waehrend es im 39-min-Ruhelauf (M-5) auf
0,59/min stieg — bei perfektem Klang. Eine Anzeige auf Underflow-Basis
haette den kaputten Fall freigesprochen und den einwandfreien angeklagt.

**Pruefe diesen Test besonders scharf:** Faellt er auch dann noch um, wenn
jemand die Logik zurueckdreht? Ein Regressionstest, der die Regression nicht
faengt, ist schlimmer als keiner.

## Der Punkt, den er als nicht erfuellbar meldet

**AK-T009-24 ist nur zur Haelfte abdeckbar.** Die Verdikt-Ebene
(`DISTURBED`, `CANNOT_TELL`, `LOSS_NOTICE_RATE_PER_MIN`,
`LOSS_ALERT_RATE_PER_MIN`) existiert im Code nicht — `grep` findet keinen
dieser Begriffe. Die heutige Anzeige baut einen Satz aus Kanalnamen und hat
keinen Zustandsbegriff.

**Bestaetige oder widerlege das durch eigene Suche.** Wenn er recht hat, ist
AK-T009-24 heute kein erfuellbares Kriterium, sondern eine Spezifikation fuer
Code, den es noch nicht gibt — und das gehoert klar so im Bericht zu stehen,
statt als „teilweise gruen" durchzugehen.

## Weitere Pruefpunkte

- **Regression:** Erwartungswert fuer einen frischen Lauf ist
  `.\gradlew.bat --console=plain test` -> **2344 Tests, 0 Failures**
  (vorher 2332/0). Weicht die Zahl ab, ist das ein Befund.
  **Achtung:** `gradlew.bat` scheitert aus der Bash-Shell mit „JAVA_HOME is
  not set" — die HKCU-Variablen aus T-010 werden nicht vererbt. Exportiere
  `JAVA_HOME=~/tools/jdk/jdk-21.0.12.1+1` und
  `ANDROID_HOME=~/tools/android-sdk` je Befehl.
- **Kopplung:** `isEmpty` wurde absichtlich **nicht** angefasst. Traegt diese
  Entscheidung, oder gibt es einen Pfad, auf dem ein abgeschnittener Dump
  jetzt anders wirkt als vorher?
- **Der 990-Fall:** Der ABR-Regler probiert 990 kbps von sich aus — 31-mal im
  M-5-Lauf, 30-mal fuer genau ein Sample, nie mit Verlust. Der Test
  `a reading of 990 kbps changes the rate and nothing else` soll festnageln,
  dass kein Feld darauf reagiert. Reicht er dafuer?
- **Der Index ist keine Bitrate.** Gemessen: 660<->1, 492<->3, 396<->4. Die
  Leiter ist nicht monoton. Gibt es im Code irgendeine Stelle, die den Index
  doch wie eine Rate behandelt?
